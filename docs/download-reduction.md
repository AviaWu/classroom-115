# 下載優化 A／B／C 階段

## 範圍

A 實作備份／刷新讀取縮減、receipt 查詢合併、保守的佇列排空，以及無變更標記清理。B 採下述保守相容方案：縮小操作投影讀取與更新範圍，但持久化同步計畫維持完整。C 僅新增協力未達標且無個人／投影變更的短流程。未變更資料結構或權限規則。

## 行為與確定性預算

- [完整進度 reader](../public/firebase-store.mjs:202) 優先使用專用資料來源，缺少專用來源時仍相容既有完整來源與舊版進度來源。專用來源失敗不偷偷回退。保留房間同步鎖與 projecting receipt 阻擋，以及成員／權威個人資料驗證。
- [瀏覽器接線](../public/index.html:3484) 每次備份或刷新讀取房間、學生 UID 對照、學生個人狀態，共 **3 個伺服器 GET**，原先為 6 個。不下載寵物及公開投影；不以訂閱快取代替伺服器讀取。完整畫作仍依原流程另讀最近三張。
- [receipt 查詢](../public/cloud-sync.mjs:103) 在同一生命週期，每筆待確認操作最多一個進行中查詢。即時快照收到負結果後冷卻 **5 秒**；明確刷新／排空略過冷卻，但共用尚未完成的查詢。重新連線、恢復活動會重新查證。沒有 receipt 並非操作失敗，待確認操作不會被移除或自動重送。
- [佇列排空](../public/cloud-sync.mjs:188) 只在有效、連線、已驗證且有即時訂閱時省略完整讀取；無待確認 receipt 的排空為 **0 個完整 GET**。未驗證或沒有即時訂閱時保留刷新。待確認操作、失去連線、生命週期切換、排空期間操作拒絕均不可誤報成功；不確定的寫入保留原操作識別碼。
- [標記清理](../public/firebase-store.mjs:395) 若目標標記已不存在、學生已刪除，或已換成另一筆操作標記，交易 updater 中止，不寫入相同值。這仍需要 **1 個 ETag GET、0 個 PUT**；匹配標記為 **1 GET、1 PUT**。PUT 衝突後重讀若發現新標記，立即中止，不覆蓋新獎勵或新標記。

## 回歸驗證

- [同步測試](../tests/cloud-sync.test.mjs)：可控制時鐘與延遲回應；覆蓋快照連發、查詢合併、冷卻、重連、隱藏／恢復、釋放、明確重試競爭、排空與寫入失敗。
- [儲存測試](../tests/firebase-store.test.mjs)：專用 reader 與 fallback、權威個人值、同步阻擋、ETag 清理預算、重播及獎勵不重複。
- [頁面接線測試](../tests/page-integration.test.mjs)：透過實際頁面模組與模擬 REST transport 驗證精確讀取路徑、禁止快取、備份新鮮度及同步阻擋。
- 完整測試入口維持 [套件測試設定](../package.json:6)。測試均為本機模擬，沒有讀取正式資料庫或執行部署。

## 限制

1. 三個分支為平行伺服器讀取，沿用既有跨分支非原子快照語意。阻擋檢查針對讀到的房間狀態，不宣稱能凍結讀取期間其他裝置的操作；未新增版本號或跨分支一致性協定。
2. 五秒冷卻沒有背景輪詢計時器：後續快照、明確刷新／重試或重連會再查證。自動顯示恢復結果可能延後；不會因查無 receipt 判定失敗。
3. 生命週期切換會忽略舊查詢結果，但不取消已送出的 HTTP 請求；重連後可能與舊請求短暫重疊，以免舊連線阻塞新生命週期。
4. 排空不是最新快照 API，也不等待整個班級的所有遠端操作；備份仍獨立讀取伺服器。既有 verified 訊號來自訂閱／成功讀取，未新增 Firebase 連線驗證協定。
5. 房間本身仍包含既有 receipts 與完整同步計畫，標記清理仍需讀取學生狀態。持久化計畫縮減延後，原因見以下 B 相容性決策。未量測正式環境位元組量，也未執行 emulator 或正式多裝置驗證。

## B：依操作縮小投影讀取與更新（保守相容版）

### 新舊客戶端安全決策

舊版恢復器把缺少的投影當成空值，再清除既有資料。因此 **不得輸出省略無關投影的 compact 持久化計畫**。本輪沒有使用版本欄位假裝能阻擋不認識版本的舊頁面，也沒有新增部署 gate 或規則。

[計畫產生器](../public/teacher-sync-plan.mjs:69) 保持原本完整格式：個人計畫、全班寵物、公開 BOSS 與公開題庫都照舊產生。Firebase 原生空節點省略仍按舊格式的空集合語意處理，沒有引入「省略代表不更新」的新線上格式。新舊分頁接手同一計畫時有相同完整資料。

[範圍計算](../public/teacher-sync-plan.mjs:41) 僅在記憶體中保存，根據交易中的前後投影差異計算；不寫入資料庫。每次 ETag 重試清除前次範圍，僅使用成功交易的範圍。重新載入、遺失回應或其他分頁接手未完成計畫時，一律完整讀取／修復投影。這是保守回退，不是完整 B compact-plan 目標已完成。

### 操作路徑

- [頁面初始讀取](../public/index.html:3471)：讀房間、UID 對照、全班權威個人狀態，共 3 GET；不用訂閱快取。
- [投影讀取及更新](../public/firebase-store.mjs:404)：交易成功後才依範圍讀取。普通衣服／背景購買、任務和資源獎勵不另讀也不更新無關投影；寵物購買只讀投影實際改變的學生。抽獎依最後成功抽到的商品決定範圍。
- 寵物互動與 BOSS 攻擊仍在個人 ETag 交易重算條件式結果，不重複發獎；公開資料由完整房間產生，無需另讀相同公開分支。
- 還原、初始化、商品／BOSS／題庫編輯、清空衣櫃、學生增刪及其他管理操作保留全投影讀取與修復。未列入一般操作白名單的操作預設完整範圍。
- 還原仍設定時間屏障；先增補必要寵物再更新個人狀態，最後移除不再需要的寵物。舊版未完成計畫不依目前使用者準備執行的命令縮減。
- 請求的投影欄位若被自訂 reader 漏掉，則在個人／公開投影寫入前拒絕；不存在的伺服器節點必須明確回傳空值。縮減初始 reader 必須搭配投影 reader，否則在鎖定前拒絕。
- 個人狀態加法、條件式重算、同步標記、已完成收據和最終權威狀態刷新維持原機制。REST 條件寫入仍使用伺服器 ETag，沒有靜默條件寫入，也沒有改回 SDK 交易。

### Fixture 預算與回歸

[操作讀取測試](../tests/operation-read-budgets.test.mjs) 直接執行頁面的接線及真實 REST client，僅替換傳輸。Fixture 為 28 人、每人已有一隻寵物、含長圖片路徑及 40 題公開題庫。位元組為 UTF-8 JSON body，不含 HTTP/TLS、壓縮、訂閱流量或 Firebase 計費開銷。時間戳使用固定長度數字；測試比較完整讀取與縮減讀取路徑。

| 操作 | 額外投影 GET（原 3） | 額外投影讀取 bytes（原 35,615） | 避免的 fixture bytes | 完整操作 GET（原 12） | 寫入 body bytes |
| --- | ---: | ---: | ---: | ---: | ---: |
| 衣服購買 | 0 | 0 | 35,615 | 9 | 90,969 |
| 背景購買 | 0 | 0 | 35,615 | 9 | 90,939 |
| 個人任務 | 0 | 0 | 35,615 | 9 | 88,520 |
| 寵物購買 | 1（單一學生） | 581 | 35,034 | 10 | 93,897 |

完整操作 GET 包含初始資料、兩次房間 ETag 讀取、個人更新與清標記 ETag 讀取、最終對照／個人狀態刷新。寫入 body 合計包含條件 PUT 及多路徑更新；各案例硬上限 100,000 bytes，完整讀取與縮減讀取版本的寫入量必須相等，**寫入請求節省為 0**。房間交易仍會攜帶完整計畫（本 fixture 約 36–37 KB），所以不能宣稱整筆操作不再傳輸無關投影，或把上表解釋為實際費用節省。

測試另覆蓋：

- 缺少所需投影讀取的拒絕與完整恢復、缺少配對 reader 時不得先寫鎖。
- 新版完整計畫交給凍結的舊版投影更新演算法不會清除資料；compact 負向對照確實會清除，用來防止誤把省略當安全。
- 舊客戶端先套用個人獎勵、新客戶端接續恢復不重複發獎；舊完整計畫先恢復，再執行無關新命令。
- 房間重試後持有狀態／價格變動、抽獎在衣服與寵物間切換；個人狀態重試保留其他獎勵及互動欄位。
- 映射改變導致重複個人資料時拒絕完成，不把舊獎勵改投新 UID；修復映射後沿用標記安全恢復。
- BOSS／題庫／商品刪除完整修復、相等備份仍完整還原與時間屏障、條件獎勵競爭。

### 本機驗證結果

2026-10-07 全套 Node 測試通過 **300 項**（A 既有 280 項＋B 新增 20 項），差異空白檢查通過。沒有讀取正式資料庫、部署、推送、提交或修改安全規則。

### 尚未完成／限制

1. **延後 compact 持久化計畫與相關房間 request/response 縮減**。若後續要做，需先另行核准並驗證能實際阻擋舊寫入端的版本協議／部署 gate／規則；僅要求使用者關閉舊頁面或只加版本欄位不足以保證安全。
2. 完整房間及全班個人狀態仍會讀取；本輪只縮小額外投影分支。正常一般操作不順便修復無關既有投影漂移；恢復及管理操作仍完整修復。
3. UID 對照與個人狀態依舊不是跨分支原子快照；本輪不提供線上映射遷移協議。異常狀態可能留下待恢復鎖，須修復資料或重試，不會自動改投獎勵。
4. C 的短流程範圍與限制見下節；其他任務、metadata 與畫作未擴大短流程。正式環境、emulator、實體新舊分頁連線及計費量測均未執行。

## C：協力未達標短流程

### 安全條件與寫入內容

- [協力 coordinator](../public/firebase-store.mjs:461) 在**每次 ETag updater** 使用最新房間與當前時間重算協力結果，不沿用初始未達標判斷或上一次失敗嘗試的短流程旗標。還原屏障、待恢復計畫優先；有未完成收據卻缺少計畫時拒絕。房間已被刪除時不使用初始快照復活資料。
- [短流程判斷及共用欄位 patch](../public/teacher-sync-plan.mjs:54) 僅接受協力完成命令、結果尚未領獎、目前成員仍未全部完成、空個人計畫、空投影差異，以及除了目標完成名單外沒有其他 domain 變更。個人／投影有變更、最後達標（即使獎勵為零）都保留完整 coordinator。
- 通過時，**第一次房間交易同時寫完成名單及 final receipt**，不持久化同步計畫，不進行第二次房間交易、個人投影、公開／寵物投影讀寫、權威狀態再次刷新或標記清理。收據沿用原有欄位與伺服器提交時間，沒有新增版本／schema。
- 寫入進度從**當前 ETag 的原始進度**建立，只 patch 目標協力任務的完成名單及儲存時間。所有最新非協力欄位、legacy 個人欄位及 compact 欄位省略原樣保留，絕不把較早讀取的權威個人狀態 merge 後整份寫回。這是房間條件 PUT 的內容縮限，不是無條件遠端 PATCH。
- 初始仍為房間、UID 對照、全班個人狀態 **3 分支 GET**。回傳畫面使用該次讀取的個人狀態，不宣稱是跨分支原子快照；同時發生的學生個人更新由既有訂閱反映。最後達標仍對最新個人狀態套用加法獎勵及標記，完成後刷新權威狀態。

### 重播與新舊相容

- 重複操作識別碼讀 final receipt，無房間交易或個人清理；新識別碼的重複點擊則由最新完成名單判定無變更。收據淘汰後也不重複新增成員／發獎。
- PUT 已提交但網路回應遺失或成功回應 JSON 損壞時，保留原操作識別碼重試，透過原子保存的 final receipt 確認。未達標重試若變成達標，重新走完整獎勵 coordinator；反方向也重新計算。
- 新短流程沒有 pending plan 可讓舊 client 誤清投影，final receipt 是既有格式。**所有實際建立的 pending plan 仍維持 B 的完整格式**；目前／舊版未完成計畫一律完整恢復，不能套用新命令的空 scope。
- [REST／頁面接線測試](../tests/operation-read-budgets.test.mjs) 使用內容雜湊 ETag，實際執行 REST client 的 412 重讀迴圈及並行寫入。相容控制保留同一 coordinator、只停用新短流程分支，以驗證 pre-C 完整計畫／receipt 行為；另保留 B 的凍結 pre-B 投影更新演算法與缺欄位破壞性負向對照。這不等同實體舊分頁驗證。

### Fixture 預算

同前述 28 人 fixture，加一個 10 代幣協力任務。以下為無衝突、無其他 pending plan 的第一次未達標完成，對照 B 的相同完整 coordinator：

| 指標 | B（C 前） | C |
| --- | ---: | ---: |
| 全操作 GET | 7 | **4** |
| 房間交易／成功房間 PUT | 2／2 | **1／1** |
| 額外個人／寵物／公開投影讀寫 | 0 | **0** |
| 最終對照／個人狀態刷新 GET | 2 | **0** |
| GET 回應 body bytes | 123,165 | **56,152** |
| 寫入 body bytes | 88,215 | **25,979** |
| 個人標記清理交易 | 0 | **0** |

GET body 減少 **67,013 bytes**，寫入 body 減少 **62,236 bytes**。測試硬上限為 GET body 60,000 bytes、寫入 body 30,000 bytes，並與停用 C 的相同 fixture 比較。B 原本未達標沒有個人 delta，所以原本個人投影／清理也是零，不把它算成新增節省。GET body **不包含條件 PUT 的回應 body**，同樣不包含壓縮、標頭、訂閱、計費與正式資料量。

final receipt 重播為 **3 GET、0 PUT、0 房間／個人交易**；不同識別碼的重複點擊為 **4 GET、0 PUT**。單次房間 412 衝突但仍未達標為 **5 GET、2 次條件 PUT 嘗試（1 次成功）、1 次邏輯房間交易**。最後達標與待恢復計畫不適用短流程預算。

### C 回歸覆蓋

- 兩位最後成員同時完成，真實 ETag 衝突後分別累積完成；代幣／樂透券只發一次。
- 未達標轉達標／達標轉未達標，最新個人餘額保留；零獎勵達標仍走 coordinator。
- compact／legacy 狀態、並行個人餘額／裝備／任務／畫作變更保留；不把舊個人狀態寫入最新 legacy 欄位。
- 初始／重試還原屏障、pending restore 搶先提交、目前／舊版 pending plan 完整恢復、orphan 未完成收據拒絕。
- 房間／任務／成員刪除、重試跨過截止時間，不沿用過期 eligibility。
- 重複點擊、receipt 重播／淘汰、未知 PUT 網路／解析結果、跨新舊流程恢復與個人獎勵回應遺失，不重獎。
