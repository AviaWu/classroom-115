# 雲端同步重整與部署

這次改為單一最新進度與逐筆操作交易。資料庫結構及關聯圖見 [資料庫結構表](database-structure.md)。

## 使用行為

- 開頁、重新整理先讀伺服器最新進度；不把本機快取、分享網址內容、內建商品或舊版本資訊自動上傳。
- 頁面分別訂閱學生、任務、商品、BOSS、協力任務、畫作索引及設定子路徑；切回分頁、恢復焦點、重新連線時重新取得目前值，之後只接收變動的子路徑。
- 操作立即在背景送出，不顯示「處理中」或鎖住整頁。網路失敗顯示「離線中」，停用會修改資料的控制，仍可查看快取及保留草稿。權限／格式等非網路錯誤會顯示真正原因。
- 任務、購買、抽獎、穿搭、預設寵物、背景、每日好感度、協力成員、畫板儲存，以及教師設定都送出操作指令。代幣與樂透券加減、清空資源、衣櫃重設、性別／人數調整也有明確操作。
- 裝備設定以雲端最後接受的設定為準；資源加減在最新數值上計算。購買及領獎驗證同一交易中的最新狀態，避免超支或重複發放。
- 樂透的隨機樣本只建立一次；扣券、獎品／重複補償及操作收據在同一交易完成，回應遺失時重用原識別碼查證。
- 教師欄位編輯只更新指定欄位；若同一欄位已被其他裝置修改，拒絕過期編輯並保留草稿。背景更新保留視窗、頁籤、捲動、教師輸入／圖片檔案選擇及畫板 canvas；刪除中的商品草稿保留供複製。
- 每 30 秒檢查每日／每週排程，使用最新雲端模板、台灣日期與確定的任務 ID 產生；刪除標記防止任務再生。
- 一般同步只訂閱 `progress/drawings` 索引，不下載畫作圖片。只有畫板開啟時才按需讀取最新三張，未變更的 ID 使用頁面記憶體快取。

## 資料與交易

`games/classroom-115/progress` 始終是唯一最新進度。`operations/{operationId}` 保存執行結果，不保存整份進度歷史；一般只保留最近一小時且位於最新 100 筆內的收據，本機尚待確認的操作例外保留。`lastOperationId` 指向最新操作收據。日常讀取只讀 `progress`。

網頁上的即時操作使用 Firebase SDK `runTransaction()`，不再使用 REST ETag PUT，因此成功提交後不會再下載一份完整班級根節點回應。

畫作圖片獨立放在 `/artworks/classroom-115/{drawingId}`；`progress.drawings` 只保留最多三筆 `{id, savedAt}`。新增第四張時，最舊圖片透過可重試的刪除待辦移除，不建立歷史畫冊。

[Firebase 存取模組](../public/firebase-store.mjs) 在網頁中使用 Firebase SDK `runTransaction()`：讀取最新班級節點、套用操作並原子提交；衝突時 SDK 以最新資料重算同一操作。頁面不儲存或比對進度版本，也不會以瀏覽器舊快照取代雲端。REST ETag 交易僅保留給未注入 SDK 的本機工具。

首次讀取舊存檔不改寫任何資料；下一筆真正改動進度的操作才移除 `syncVersion`、`revision`、`baseCommitId`、`commitId`、`updatedAt`。雲端空白只清空畫面，由老師明確初始化或還原。

[同步控制器](../public/cloud-sync.mjs) 保留尚未確認的操作識別碼。當頁面還開著，恢復網路後先讀雲端，再查證／重試原操作；刷新頁面後只查收據，不自動重送未確認指令。教師後台「備份」頁提供「確認上次操作」。不同內容的還原或畫板存檔不會被偷換成上次待確認的內容。每筆新交易會保留最近一小時且位於最新 100 筆內的收據，並額外保留該裝置 `sessionStorage` 中尚待確認的操作 ID。

## 備份與還原

- 主畫面移除「同步備份」；老師後台選單改為「備份」。
- 「下載備份」即時讀取伺服器，匯出可直接還原的單份進度 JSON，不下載本機舊快取或操作收據。
- 「下載備份」只額外讀取最近三張完整畫作，不包含歷史畫作及刪除待辦。
- 「從備份還原」只接受最多三張有效完整畫作，配置新的畫作 ID，顯示成員／任務／畫作數量及全班覆蓋範圍，老師確認後才交易寫入。其餘裝置下次讀取更新。
- 還原／初始化保留雲端收據，設定 `restoredAt`；較早的未確認指令不能改動還原後的進度。
- 本機快取空間滿不影響已完成的雲端操作；若無法可靠保存待確認指令，會在送出前停止並報錯。

## 測試

需要 Node.js 22 以上；模擬器需要 Java 21 以上。

```sh
npm ci --ignore-scripts
npm test
firebase emulators:exec --config firebase.emulator.json --project demo-classroom-sync --only database "npm run test:emulator"
```

Node 測試涵蓋操作規則、60 秒備援輪詢、子路徑訂閱生命週期、SDK transaction、REST 回應遺失，以及真實 DOM 的草稿／視窗／畫板保留。模擬器測試使用真正資料庫規則與 REST 存取模組，強制兩台裝置讀取同一 ETag，驗證 412 衝突、重讀、扣款／領獎、收據裁切及還原；兩個測試檔共用測試資料庫，必須序列執行。

## 既有資料 migration

這次不需要搬動 `progress`、商品、任務或畫作資料，也不需要在 Firebase Console 匯入轉換後的 JSON。既有 `operations` 可以原地保留；新網頁完成第一筆「實際改變進度」的交易時，會在同一筆原子交易中自動完成以下整理：

- 移除 `progress` 內的 `syncVersion`、`revision`、`baseCommitId`、`commitId`、`updatedAt`。
- 將舊版單一 `progress/boss` 轉成目前使用的 `progress/bosses[]`，並移除舊欄位。
- 保留最近一小時且位於最新 100 筆範圍內的操作收據。
- 保留執行交易之裝置目前 `sessionStorage` 待確認佇列所列的收據。
- 保持 `progress` 其他內容與 `/artworks/classroom-115` 不變。

正式 migration 步驟：

1. 在 Firebase Console 的 Realtime Database 匯出完整 JSON 備份，記錄匯出時間與檔名。
2. 先部署新的 `database.rules.json`。舊規則若不允許在新增收據時刪除舊收據，新版網頁的第一筆裁切交易會失敗。
3. 再部署 `public`。
4. 用一個沒有待確認操作的裝置重新整理頁面，等畫面取得雲端進度。
5. 執行一筆確實會改變資料、而且容易核對的教師設定；也可以等待下一筆正常任務、購買或其他交易。只讀取頁面或送出結果沒有變化的操作不會觸發 migration。
6. 在 Console 檢查 `/games/classroom-115/progress` 內容仍正確、舊版本欄位已消失，並確認 `/games/classroom-115/operations` 通常不超過 100 筆。若該裝置有待確認項目，為保留這些收據可以暫時超過一般上限。
7. 保留步驟 1 的備份，直到多台裝置完成重新整理與至少一筆實際操作驗證。

不要直接刪除整個 `operations` 節點。仍開著或稍後恢復的裝置可能需要其中的收據判斷先前操作是否已成功；由新交易依保留規則裁切即可。

隔離的瀏覽器測試頁：`npm run preview:test`，開啟 `http://127.0.0.1:8087`。此頁只有虛構的兩位學生，完全不連 Firebase；供檢查畫面互動，不代表已部署正式網站。

## 正式部署

1. 先確認目前正式雲端資料正確，從 Firebase Console 匯出備份。
2. 先部署 `database.rules.json`，確認 `/artworks/classroom-115/{drawingId}` 規則生效。
3. 部署完整 `public`（包含 HTML 及三個 `.mjs` 模組）。根網址、HTML 與模組皆使用不快取標頭。
4. 每台裝置重新整理；確認讀取後數值一致，再測試一筆任務、購買及教師設定。
5. 儲存四張測試畫作，確認 `progress.drawings` 與 `/artworks/classroom-115` 都只剩三張，且一般輪詢沒有 `/artworks` 請求。
6. 確認另一台保持開啟的頁面在下一次讀取看到結果，且視窗、草稿與畫布仍在。

正式 GitHub workflow 執行：安裝測試依賴 → Node 測試 → Java／Firebase 規則及實際交易模擬測試 → 部署資料庫規則 → 部署 Hosting。規則部署失敗時停止，不能只部署網頁。

部署服務帳戶須具備此專案的 Realtime Database 規則部署與 Hosting 權限。遇到取得資料庫執行個體資訊失敗，應檢查 `classroom-115` 專案、`classroom-115-default-rtdb` 執行個體、Realtime Database API 與部署帳戶 IAM；不要透過放寬資料讀寫規則處理部署權限問題。

## 實作邊界

沿用現有匿名登入、共享班級及前端教師密碼模式。此次規則防止舊頁面無操作收據的寫入；業務檢查由受控客戶端交易執行，並非新增伺服器端教師／學生權限系統。蓄意自行構造請求的已登入使用者仍可能繞過業務規則或刪除較舊的整筆收據。操作去重以本次客戶端保留收據的正常使用模式為前提；若需要對抗惡意修改，需另設可信任後端及正式角色權限。

收據一般只保留最近一小時且位於最新 100 筆內；日常子路徑訂閱不下載收據或畫作圖片。畫板開啟時由畫作索引變更觸發更新，只下載尚未快取的 ID。
