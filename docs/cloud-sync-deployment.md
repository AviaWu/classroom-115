# 跨裝置存檔修正與部署

## 行為

- [同步控制器](../public/cloud-sync.mjs) 使用原始雲端版本與提交識別碼進行交易；時間僅作顯示，不決定誰可以覆蓋資料。
- 分頁恢復、取得焦點或重新連線時，先鎖定操作，透過無快取的伺服器讀取確認最新進度，再恢復遊戲。
- 存檔期间短暫鎖定操作，避免同一裝置累積不同基礎版本的寫入。離線時停止修改共用進度。
- 衝突時先保存本機備份，再清除舊寫入並套用雲端資料；備份失敗則維持鎖定，不默默丟棄本機操作。
- 「同步備份」按鈕下載本機備份及目前本機進度。備份保存在目前瀏覽器的 IndexedDB，不會自動上傳；清除網站資料會刪除它們。
- 備份下載檔是包含多筆紀錄的封裝，不可直接當作老師後台的遊戲備份匯入。復原前應挑出並檢查所需的一筆完整進度，再透過後台有意識地匯入。
- 現有存檔沒有資料版本時，第一次新版連線會在交易中比對完整舊快照，保留內容並加入第一版同步資訊。正常商品目錄校正仍會執行。
- 此方案選擇拒絕衝突，不會自動合併兩台電腦的代幣、購買、任務或刪除操作。

## 部署前

1. 暫停其他裝置操作，確認目前雲端是要保留的正確进度。
2. 在 Firebase Console 匯出 Realtime Database 備份，並從可信任的遊戲頁面匯出備份。不要為了備份去按舊分頁的儲存。
3. 保留修正前的網頁與規則版本，但不得透過放寬規則讓舊分頁重新寫入。
4. 執行 [同步測試](../tests/cloud-sync.test.mjs)、[網頁測試](../tests/page-integration.test.mjs) 與 [規則模擬器測試](../tests/database-rules.emulator.mjs)。模擬器需要 Java 21 以上。

## 正式上線順序

1. **先部署 [資料庫規則](../database.rules.json)。** 此時仍開著的舊網頁會被拒絕寫入，可能短暫顯示同步失敗。
2. **再部署 [網頁](../public/index.html) 與 [同步模組](../public/cloud-sync.mjs)。** 兩者缺一不可。
3. 在一台電腦重新載入，等待同步確認及舊資料升級完成。
4. 重新載入其他電腦的所有舊分頁。
5. 執行下方實機驗證。

[正式 GitHub 工作流程](../.github/workflows/firebase-hosting-merge.yml) 已改成：Node 測試 → Java 21 模擬器規則測試 → 部署規則 → 部署 Hosting。任一步驟失敗即停止。現有服務帳戶需要部署 Realtime Database 規則的權限；若只有 Hosting 權限，必須由專案管理者補上所需的最小權限。

請勿把只部署 Hosting 視為修正完成，因為未重新整理的舊分頁仍在執行舊程式。

## 驗證指令

以下命令需從專案根目錄執行，不會寫入正式資料庫：

    node --test tests/cloud-sync.test.mjs tests/page-integration.test.mjs
    firebase emulators:exec --config firebase.emulator.json --project demo-classroom-sync --only database "node --test tests/database-rules.emulator.mjs"

規則測試限制只能連線至本機模擬器，不接受正式 Firebase 網址。

## 實機驗證

- A 開著遊戲並切到背景；B 改變代幣並確認同步；A 回到前景必須先同步，再顯示 B 的代幣。
- A 有未完成同步的操作後斷線；B 更新；A 重連時應顯示衝突訊息，下載的備份要包含 A 的原始操作，雲端保留 B 的進度。
- A、B 同時操作：只有基於目前雲端版本的交易可以成功，另一筆不得靜默覆蓋。
- A 背景排程到點或系統時間調快／調慢：不得讓整班進度倒退。
- 刻意保留部署前的舊分頁：其寫入應收到規則拒絕。
- 離線、禁止備份儲存、無權限、雲端資料格式異常：應保持鎖定，不能切換成可任意回寫的本機模式。
- 下載同步備份，確認其中內容可讀。備份儲存與畫面互動仍需真實瀏覽器驗證。

## 此次本機驗證狀態

同步與網頁整合測試通過。Firebase 模擬器未能啟動：本機 Java 8 不符合 Firebase CLI 15.30.0 的 Java 21 要求。規則測試已加入部署前檢查，但不能把尚未執行的 CI 或實機驗證宣稱為已通過。

此次編輯未部署正式 Hosting 或資料庫規則，也未修改正式雲端遊戲進度。部署後才會對線上使用者生效。

## 部署錯誤：無法取得資料庫執行個體資訊

若部署在取得執行個體資訊時失敗，這不是足以證明規則語法錯誤的訊息。原先只部署 Hosting 的 GitHub 服務帳戶可能沒有管理 Realtime Database 的權限。

1. 執行更新後的 [正式工作流程](../.github/workflows/firebase-hosting-merge.yml)，查看「Deploying as」顯示的服務帳戶電子郵件。該資訊不是私鑰；不要公開或貼出完整服務帳戶金鑰。
2. 由專案管理者前往 Google Cloud Console → 選擇 classroom-115 → IAM 與管理 → IAM。
3. 找到上一步的服務帳戶，在 classroom-115 專案授予 **Firebase Realtime Database Admin** 角色。若使用自訂最小權限角色，需由管理者核對 CLI 列出、取得執行個體及部署規則所需權限。不要為了排錯授予 Owner 或 Editor，也不要放寬遊戲資料庫讀寫規則。
4. 確認 Firebase Console → Realtime Database 中存在 classroom-115-default-rtdb，位於 asia-southeast1。若錯誤明確表示 API 未啟用，再由管理者檢查 Firebase Realtime Database 管理 API。
5. 等待 IAM 權限傳播後重跑工作流程。已新增手動觸發，無須為重試修改遊戲資料。
6. 如果仍失敗，需要查看該次 GitHub 執行的除錯紀錄，而不是本機舊紀錄。403 通常指向權限、API 或組織政策；404 則應核對專案與執行個體。分享紀錄前移除憑證、權杖與私鑰。

新版工作流程會先驗證憑證基本格式、顯示帳戶身分並列出可存取的資料庫；任何一步失敗都不部署 Hosting。此檢查不會自動修改 IAM，也不能取代管理者授權。

## 範圍限制

本次防護處理合作式客戶端的過期寫入，不是使用者權限重設。現有匿名登入仍可存取共用班級進度；若需防止未授權使用者蓄意修改，應另行加入正式登入、角色權限及伺服器端業務驗證。
